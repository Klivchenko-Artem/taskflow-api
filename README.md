# Task Tracker API

REST API трекера задач на Laravel 13: проекты, участники, задачи, комментарии.
Токенная авторизация через Sanctum, права доступа на политиках, уведомления
через очередь Redis, документация OpenAPI, 82 теста, запуск одной командой
в Docker.

Пет-проект, написан для демонстрации бэкенд-части: чистое API без интерфейса.
Фронтенд к нему лежит в отдельном репозитории taskflow-web.

## Стек

| Слой | Технологии |
|---|---|
| Бэкенд | PHP 8.3, Laravel 13 |
| Авторизация | Laravel Sanctum (Bearer-токены) |
| База | PostgreSQL 16 (тесты на SQLite в памяти) |
| Очередь | Redis 7 и отдельный контейнер-воркер |
| Почта | Mailpit в docker compose, письма видно в браузере |
| Документация | OpenAPI 3.0 через L5-Swagger, PHP-атрибуты |
| Тесты | PHPUnit 12, 82 теста |
| Запуск | Docker и docker compose (php-fpm, nginx, postgres, redis) |

## Запуск

```bash
docker compose up -d --build
```

- API: http://localhost:8000/api
- Swagger UI: http://localhost:8000/api/documentation
- Mailpit: http://localhost:8025

Порты можно сменить через `HTTP_PORT` и `MAIL_UI_PORT`. Миграции накатываются
при старте.

## Модель данных

```
User ──владеет──> Project <──участвует──> User   (many-to-many, роль в pivot)
                     │
                     └──> Task ──> Comment ──> User
                           │
                           └──назначена──> User
```

- Project: проект с владельцем и списком участников;
- Task: задача внутри проекта, у неё статус (todo, in_progress, testing, done), приоритет, срок и исполнитель;
- Comment: комментарий участника к задаче.

Статусы и приоритеты сделаны PHP-перечислениями (`App\Enums\TaskStatus`,
`App\Enums\TaskPriority`), а не строками россыпью: правила валидации и приведение
типов берутся из одного места.

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/register` | Регистрация, сразу выдаёт токен |
| POST | `/api/login` | Вход, выдаёт токен |
| POST | `/api/logout` | Отзывает текущий токен |
| GET | `/api/me` | Текущий пользователь |
| GET | `/api/projects` | Проекты пользователя, постранично |
| POST | `/api/projects` | Создать проект |
| GET | `/api/projects/{project}` | Проект с участниками |
| PUT | `/api/projects/{project}` | Изменить проект |
| DELETE | `/api/projects/{project}` | Удалить проект (только владелец) |
| POST | `/api/projects/{project}/members` | Добавить участника по id или почте (только владелец) |
| GET | `/api/projects/{project}/tasks` | Задачи проекта с фильтрами |
| POST | `/api/projects/{project}/tasks` | Создать задачу |
| GET | `/api/tasks/{task}` | Одна задача |
| PUT | `/api/tasks/{task}` | Изменить задачу |
| DELETE | `/api/tasks/{task}` | Удалить задачу |
| GET | `/api/tasks/{task}/comments` | Комментарии к задаче |
| POST | `/api/tasks/{task}/comments` | Добавить комментарий |
| GET | `/api/users?search=…` | Подсказки для приглашения, поиск от трёх символов |

Подсказки отдают только идентификатор и имя. Имя ищется подстрокой, почта только
целиком, иначе адрес можно было бы восстановить перебором по символам. Параметр
`exclude_project` принимается только для своих проектов.

Фильтры списка задач: `status`, `priority`, `assignee_id`, `due_before`
(в формате `YYYY-MM-DD`) и `search`. Они считаются запросом к базе и
комбинируются между собой. Поиск идёт без учёта регистра.

## Пример работы

```bash
# регистрируемся и забираем токен
curl -X POST http://localhost:8000/api/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Артём","email":"artem@example.com","password":"secret123","password_confirmation":"secret123"}'

# создаём проект
curl -X POST http://localhost:8000/api/projects \
  -H "Authorization: Bearer ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"name":"Переезд на новый сервер"}'

# ставим задачу
curl -X POST http://localhost:8000/api/projects/1/tasks \
  -H "Authorization: Bearer ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"title":"Настроить бэкапы","priority":"high","due_date":"2026-10-01"}'

# смотрим только срочные незакрытые
curl "http://localhost:8000/api/projects/1/tasks?priority=high&status=todo" \
  -H "Authorization: Bearer ТОКЕН"
```

## Уведомления через очередь

Когда задачу назначают на человека или комментируют его задачу, ему уходит
письмо. Отправка вынесена в очередь Redis: HTTP-запрос не ждёт почтовый сервер,
письмо отправляет отдельный контейнер-воркер.

- четыре попытки, между ними минута, пять и пятнадцать минут;
- письмо не уходит, если человек назначил задачу сам на себя или комментирует
  собственную задачу, а также если за время ожидания в очереди задачу
  переназначили на другого;
- задачу или комментарий удалили до отправки: задание просто снимается с очереди;
- при смене статуса письма нет, иначе перетаскивание задач по доске засыпало
  бы почту;
- если сам Redis недоступен, задача всё равно создаётся, а ошибка уходит в лог:
  клиент не получает 500 и не создаёт дубль повторным запросом;
- текст задач и комментариев в письме экранируется, разметка из него не
  превращается в ссылки.

Проверить вживую: создать задачу с исполнителем и открыть http://localhost:8025

## Права доступа

Разграничение сделано на политиках (`app/Policies`) и проверяется ещё до
валидации запроса:

- проект видят и правят только его участники;
- удалить проект и добавить людей может только владелец;
- задачи и комментарии доступны участникам проекта, которому принадлежит задача;
- исполнителем можно назначить только участника этого же проекта.

Постороннему любая чужая запись отвечает `404`, так же как несуществующая:
по разнице в ответах нельзя пересчитать чужие проекты и задачи. Участник без
прав владельца получает `403`, неавторизованный `401`.

Вход и регистрация ограничены по частоте: 10 попыток в минуту на пару почта и
адрес и 60 в минуту на адрес.

## Тесты

```bash
php artisan test
```

82 теста на SQLite в памяти. Покрыто: регистрация и вход, отзыв токена, доступ
без токена, изоляция чужих проектов и задач, одинаковый ответ постороннему до и
после валидации, правила валидации и кривые фильтры, постраничная выдача,
каскадное удаление, подсказки по людям, кому уходят уведомления и попадают ли
они в очередь, падение очереди.

В контейнере тесты гоняются через `make test`: переменные окружения контейнера
главнее `<env>` из `phpunit.xml`, поэтому make передаёт их явно. Если запустить
тесты мимо make, они откажутся стартовать, а не пересоздадут базу стенда.

## Структура

```

  Notifications/         письма о назначении и комментарии (ShouldQueue)
  Http/
    Controllers/Api/     Auth, Project, Task, Comment, User

```

## Решения

Фильтры вынесены в scope модели. `Task::filter()` собирает запрос через
`when()`, контроллер остаётся коротким, а фильтры комбинируются в любом
сочетании без ветвлений.

Индексы поставлены под реальные запросы. Составной индекс `(project_id, status)`
нужен потому, что задачи всегда запрашиваются внутри проекта и чаще всего с
фильтром по статусу.

Ответы отдаются через API Resources. Формат описан в одном месте, пароль и
служебные поля наружу не попадают, связанные данные подгружаются только когда
нужны (`whenLoaded`).

Документация живёт рядом с кодом: описание эндпоинтов лежит PHP-атрибутами над
методами контроллеров и не расходится с реализацией. Swagger UI собирается из
них автоматически.
